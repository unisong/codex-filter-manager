# 两条维护线

| 维护线 | 仓库 | 内容 | 版本 |
| --- | --- | --- | --- |
| 全功能主线 | [codex-filter-manager](https://github.com/unisong/codex-filter-manager) | CC Switch 独立服务与 UI、`magpie-workbench/` 完整 Magpie 工作台 | `1.x`；服务内部版本另行标示 |
| 社区纯过滤 | [magpie-codex-history-filter](https://github.com/unisong/magpie-codex-history-filter) | 无 import 的请求中间件、Options、过滤测试、README 与许可 | `0.1.x`；与社区包相同 |

`magpie-community/plugins` 的 fork 只是提交上游 PR 的工作副本，不是第三个独立产品或发版仓库。

## 开发与同步

1. 新功能、UI、工作台和兼容修复先进入全功能主仓库。CC Switch 使用根目录服务，Magpie 加载完整工作台；两者的保护机制分别验证。根目录服务识别到 Magpie 配置时拒绝启动并提示正确入口，不注册旧插件或改写其接入地址。
2. 只将适用于社区中间件的过滤改动同步到插件仓库，附回归用例；不带入后台、检测、保护、UI、个人规则或运行数据。
3. 插件仓库与上游 `packages/codex-history` 保持同版本、同过滤行为、同安装文件。向社区提交 PR；合并后核对 `dist` 的实际版本、完整性与分发结果，再发布同版 GitHub Release。
4. 主线与插件版分别递增版本，不能互相比较数字大小。一次 UI 更新可只发布主线；一次过滤修复可能分别发布主线 `1.x` 和插件 `0.1.x`，在说明中记录对应关系。
5. 上游直接修复了过滤问题时，应回同步插件镜像与主仓库适配器，避免长期维护两套不同过滤行为。

当前社区纯过滤版为 v0.1.1。旧 v0.2.0 / v0.2.1 合并工作台不属于该维护线；其源码已收回主仓库，本地已安装的旧工作台不会因仓库整理而自动替换。

## 发布与本地安装

主仓库 Release 提供 CC Switch 服务和 Magpie 工作台源码。早期「独立管理服务＋Magpie 历史钩子」入口、自动注册和配套管理逻辑已移除，不再维护。完整工作台按 `magpie-workbench/README.md` 加载，使用 Magpie 原生过滤设置页和可选模型监测后台。

Magpie 用户在完整工作台和社区过滤包之间选择一种，不重复启用。公共源码、已安装目录、运行数据是三种不同用途：源码用于开发，安装目录供 Magpie 引用，数据目录保存用户状态。不能通过删除旧源码来顺带删除正在使用的安装目录或检测数据。

维护一份全功能源码、一份社区过滤源码、一个当前安装目录即可。提交社区时临时创建 fork 工作副本，合并后移除未使用的工作树。历史版本通过 Git 提交查阅，不长期保留多份解压目录。
